# Backlog File Format

The line format used in `fab/backlog.md` is the public contract between `idea` and any external consumer. This document specifies that contract.

## Pattern

```
- [ ] [{ID}] [{issue_ids}] {YYYY-MM-DD}: {description}
```

Issue IDs are optional. The pattern is the same for open (`- [ ]`) and completed (`- [x]`) items.

The line format describes two distinct shapes:

- **Shape A — idea-managed**: `- [ ] [{ID}] {YYYY-MM-DD}: {description}` (no second bracket). Idea parses, queries, and edits these lines. Round-trip preserved.
- **Shape B — pass-through**: any line that includes additional content between `[{ID}]` and the date (e.g., the optional `[{issue_ids}]` bracket). Idea does NOT match these against its parser regex. Such lines are treated as **inert pass-through content** — equivalent in idea's eyes to a header, prose line, or comment. Round-trip preserved verbatim per Constitution principle I, but invisible to `idea list`, `show`, `done`, `edit`, and `rm` operations.

External consumers (such as fab-kit's `/fab-new`) parse `[{issue_ids}]` independently and are not constrained by idea's parser shape.

## Examples

With an issue ID (Shape B — pass-through):

```
- [ ] [ni3o] [DEV-1011] 2026-02-12: Capture more metrics
```

> Note: this form is preserved verbatim by `idea` on round-trip, but is NOT visible to any `idea` query — it is treated as inert content (equivalent to a header line). External consumers like fab-kit's `/fab-new` parse the issue-ID bracket independently.

Without an issue ID (Shape A — idea-managed):

```
- [ ] [ngaw] 2026-02-23: Quality gate
```

## Components

These are the fields `idea` parses on Shape A lines and uses for query/edit/done operations:

- `[{ID}]` — 4-character lowercase alphanumeric backlog ID, unique within the file (e.g., `[ni3o]`). Generated by `idea` and used as the addressable handle for `idea show`, `done`, `reopen`, `edit`, `rm`.
- `{YYYY-MM-DD}` — ISO date the item was added.
- `{description}` — free-form description text. Searchable by `idea show <substring>` and other description-matching queries. May include tags or any other plain content.

## Opaque Pass-Through Fields

The optional `[{issue_ids}]` bracket — and any other content placed between `[{ID}]` and the date — causes the line to fall into **Shape B**. Idea's parser regex requires the date to follow `[{ID}]` directly (separated by a single space), so the entire line is rejected by the parser when a second bracket is present. Concretely:

- The line is **not** matched by idea's parser regex (`^- \[([ x])\] \[([a-z0-9]{4})\] (\d{4}-\d{2}-\d{2}): (.+)$`).
- The line is therefore treated as **inert pass-through content** — semantically equivalent to a section header, blank line, or prose line. From idea's perspective, the entire line (not just the `[{issue_ids}]` slot) is non-idea-managed.
- Even though the line **looks** like an idea entry — it begins with `- [ ]` and contains a 4-char `[ID]` — idea does NOT recognize it as one. It will not appear in `idea list`, cannot be addressed by `idea show <id>`, and is not affected by `idea done`/`edit`/`rm`.
- The line **is** preserved byte-for-byte through any idea operation that round-trips the file (per Constitution principle I).
- The semantics of the `[{issue_ids}]` slot — and of Shape B lines generally — are owned by **external consumers**. For example, fab-kit's `/fab-new` writes Linear-style issue IDs (e.g., `[DEV-1011]`) into the slot and parses them back independently of `idea`.

This design lets `idea` and external tooling share the same backlog file without one tool needing to understand the other's metadata.

## Round-Trip Preservation

Per Constitution principle I (Plain-Text Backlog as Source of Truth), parsing and re-serializing `fab/backlog.md` MUST preserve all non-idea content verbatim. This applies at two levels:

1. **Between lines** — section headers, blank lines, and prose between items are first-class content and pass through unchanged.
2. **Whole lines that look like idea entries but aren't** — any line that does not match idea's parser regex (including Shape B lines with the optional `[{issue_ids}]` bracket) is preserved verbatim. Such lines are non-idea-managed from idea's perspective, even though they superficially resemble idea-managed entries.

The file is meant to be hand-edited; the tool exists to reduce friction over hand-editing, not to take ownership of the file or its embedded metadata.

## Stability Commitment

The format spec describes both shapes for clarity. Idea's parsing contract, however, covers only Shape A. Specifically:

- **For Shape A lines** (no second bracket): idea's contract covers parsing, query, edit, and round-trip preservation. The `[{ID}]` format (4-char lowercase alphanumeric, unique within the file) and the `{YYYY-MM-DD}` ISO date format are part of the public API.
- **For Shape B lines** (with a second bracket such as `[{issue_ids}]`): idea's contract covers round-trip preservation **only**. The line stays bytes-identical through any idea operation, but no semantic operations apply — the line is invisible to `list`, `show`, `done`, `edit`, and `rm`.
- **Issue-ID-bracket semantics**: explicitly NOT part of idea's contract. The `[{issue_ids}]` slot — and any query, parse, or edit semantics for it — is owned by external consumers (e.g., fab-kit's `/fab-new`) that read and write Shape B lines.

This format is the public API. The Shape A parsing contract will not change across versions of `idea` without a major-version bump and a documented migration path. See also [Constitution principle I](../../fab/project/constitution.md) on plain-text backlog preservation, which extends to Shape B lines: from idea's perspective, they are non-idea-managed lines preserved verbatim.
